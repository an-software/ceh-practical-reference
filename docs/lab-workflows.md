# Cross-topic lab workflows

| Lab objective | Evidence and next step |
| --- | --- |
| Find RDP/MSSQL/MySQL hosts | Scan 3389/1433/3306, confirm service versions, then corroborate OS/domain metadata |
| Recover a lab FTP file | Validate the supplied/recovered account, list authorized paths, retrieve just the requested file and hash it |
| Identify a modified file | Compare requested digest and file bytes against a trusted original |
| Find hidden image/text content | Identify container type, inspect metadata, select [Steghide](../tools/steghide.md)/[OpenStego](../tools/openstego.md)/[SNOW](../tools/snow.md) appropriately |
| Interpret packet credentials/ports | Identify protocol, endpoints, stream and encryption limits; avoid inferring credentials from status alone |
| Investigate suspected DoS | Compare source/destination rates, flags, completed handshakes and capture loss |
| Identify an executable entry point | Read PE/ELF headers, validate architecture and address interpretation |
| Locate a suspicious service/RAT | Correlate process, listening port, executable path and host identity; do not guess a universal RAT port |
| Recover synthetic application data | Confirm authorization and selected parameter/schema; retrieve only the lab-required fields |

## Android and [ADB](../tools/adb.md)

For an emulator or device you own and have explicitly enabled for debugging, start with the Android SDK tool itself:

```bash
adb devices -l
adb -s emulator-5554 shell getprop ro.build.version.release
adb -s emulator-5554 shell id
```

Tools in this example: [Android Debug Bridge (adb)](../tools/adb.md).

Use the actual listed serial. USB debugging requires device authorization; modern wireless debugging may require pairing. A network-connected phone is not automatically an authorized [ADB](../tools/adb.md) target. Do not assume [ADB](../tools/adb.md) can read protected app storage. Disconnect/revoke test debugging access when finished. The original reverse-APK and wrapper examples remain in the local source archive for context; no payloads or APKs are generated by this repository.

## Exploit-reference triage and lab sessions

```bash
# Search a locally installed Exploit-DB index, without executing a result:
searchsploit 'EXACT PRODUCT VERSION'
searchsploit --nmap evidence/services.xml
```

Tools in this example: [SearchSploit](../tools/searchsploit.md).

Check product, affected version, architecture, authentication requirements and patch/backport status. A matching search result is not proof that a target is vulnerable. [Metasploit](../tools/metasploit.md) payloads and handlers must agree on payload type, architecture and connection direction. LHOST means the callback address reachable from the lab target, not necessarily your PC's main address; a VPN/NAT route can prevent connection even with correct credentials. First identify the current session's host and user rather than assuming it is the target named in a task.

The imports discuss reverse shells, [PowerUp](../tools/powerup.md), RATs, covert channels, macro delivery, [TheFatRat](../tools/thefatrat.md) and log clearing. Those are distinct concepts: remote access, privilege assessment, concealment, execution and anti-forensics. They are not all needed for a practical finding. No imported script or exploit is installed or executed by this collection. Use isolated disposable exercises and preserve evidence when validating lab behavior.

## Working through linked tasks

Maintain a host/service table and an evidence path per target. Reuse lab credentials only where explicitly permitted, track which identity produced each observation and distinguish “login works” from “file readable.” Record negative results and return to uncertain leads after resolving routing, privileges or format issues. Do not copy task-specific answers, hardcoded passphrases or file paths from old anecdotes as assumptions about a new lab.
